dbeval: Week 0 Final Evaluation Report

Research Question: Does structuring business rules inside semantic layer tools (ktx, Wren Engine, Datus) improve LLM SQL generation beyond simply pasting those rules directly into the prompt (baseline_rules)?

1. Executive Summary & Decision

The Finding

On the rules-heavy database (appdb), encoding business rules inside semantic layer tools produces substantial gains over a raw schema baseline (+21 to +24 net questions passed), but lands within 0 to 3 questions of pasting the rules into the prompt (baseline_rules), and none sits reliably above it: - baseline: 4.0 / 32 (12.5%) - baseline_rules: 28.0 / 32 (87.5%) - wren_reviewed (with engine rewrite & dialect transpile): 28.0 / 32 (87.5%) — net $+0.0$ questions vs. prompt rules (tied) - ktx_reviewed: 26.33 / 32 (82.3%) — net $-1.67$ questions vs. prompt rules - datus_reviewed (with free-text drop-in): 26.33 / 32 (82.3%) — net $-1.67$ questions vs. prompt rules - datus_reviewed_defonly (definition comments only): 25.33 / 32 (79.2%) — net $-2.67$ questions vs. prompt rules

At our sample size (32 appdb questions, 18 olist questions), every reviewed tool is within 0 to 3 questions of baseline_rules, and all 95% paired bootstrap confidence intervals span zero. There is no evidence of an advantage for tool structures over prompt rules at this sample size.

Open Question / Next Step: Rule Capture and Verification, Untested

Per the pre-registered decision framework in docs/DAY5_PROTOCOL.md: - A "Go" on a neutral comparative scoreboard between these tools is not supported, because no tool is reliably distinguishable from another or from baseline_rules. - A "Stop" is rejected, because the rules effect itself is massive and unequivocal: explicit rules lift accuracy from $12.5\%$ to $87.5\%$ on appdb. - Open question / next step: rule capture and verification, untested. The rules are the primary lever, not the tool structure. Future work should focus on exploring whether automated rule capture, induction, and verification (discovering candidate rules directly from databases and query logs) is tractable, rather than benchmarking static semantic layer formats.

4. Deep-Dives & Failure Attributions

A. Wren Engine Execution, Arithmetic Audit & Pipeline Artifacts

  1. The AppDB Execution Artifact & Arithmetic Audit: - In initial runs, Wren scored 25/32 because the LLM generated SQL referencing calculated fields (subscriptions.is_churn, accounts.is_real_account). Since Postgres lacks those physical columns, queries aborted with UndefinedColumn errors. - Resolution: Routing queries through session.transform_sql (the compiled native Wren Rust core) dynamically expands model definitions into inline CTEs before Postgres execution. - Arithmetic Semantics Audit: Because DuckDB transpilation uses floating-point division (/) whereas Postgres truncates integer division, we audited whether Wren's score lift to 28.0 / 32 (87.5%) resulted from engine arithmetic masking integer-division errors (e.g. / 100). An audit of all changed questions (appdb-005, 011, 025, 033) confirmed that zero / 100 money questions flipped between runs. All currency queries already explicitly cast amount_cents::numeric / 100 per prompt business rules. The score change was driven by LLM query variation: appdb-005 (1/3 to 3/3) properly qualified s.plan_tier to prevent column ambiguity on joins, while appdb-011 (2/3 to 3/3) consistently adopted the expanded is_churn and is_real_account calculated columns.
  2. The Olist Dialect Fix and Qualification Rendering Artifact: - Dialect Fix & Re-Run: Three Olist failures (olist-011, olist-018, olist-022) occurred because Wren Engine's SQL rewrite pass translated ROUND(AVG(...), 2) by inserting DuckDB-style CAST(... AS DOUBLE), causing Postgres to abort with type "double" does not exist. Transpiling queries via sqlglot.transpile(sql, read="duckdb", write="postgres") resolved all three questions across 3/3 runs, lifting Wren's Olist score to 14.0 / 18 (77.8%). - olist-001 Context Rendering Artifact: "How many sellers are there?" failed in 3/3 runs because the model wrote FROM olist.sellers. The prompt context header emitted DATABASE: olist, prompting the model to qualify the table with the database name instead of the schema public.sellers. This is a context rendering artifact rather than a failure of semantic rule adherence (measured 14.0 / 18; 15.0 / 18 if olist-001 had passed, matching baseline_rules). - True Rule Adherence Misses on Olist:
    • olist-006 (3/3): The generated query averaged raw payment installment rows directly rather than utilizing the order_payment_totals view defined in the layer.
    • olist-007 (3/3): The query counted customer_id (a per-order identifier) instead of joining to customers and counting customer_unique_id.
    • olist-008 (2/3): In 2 of 3 runs, an unjoined cc_orders alias was referenced; it passed in run 3.

B. The Datus "Drop-In" Effect

The initial evaluation permitted an optional rules.md file in the Datus working directory. Inspection showed that the reviewer copied all 14 appdb rules and all 8 olist rules verbatim into this file, turning Datus into baseline_rules with extra DDL. - Stripping rules.md and testing definition-only comments (datus_reviewed_defonly): - appdb: dropped from 26.33 to 25.33 (-1.0 question / -3.1 points) - olist: dropped from 16.33 to 14.67 (-1.67 questions / -9.2 points) - In the Gate D smoke test, definition-only Datus failed the Q3 net revenue test (getting 259,460.21 vs gold 258,794.23) because without rules.md, it reverted to the anti-pattern of a single LEFT JOIN refunds with invoice date filtering.

C. Gate C Value List Verification

All reviewed semantic layers were audited against PostgreSQL SELECT DISTINCT queries: - plan_tier: All tools correctly specified starter, growth, and scale. The legacy signup values (pro, enterprise) were flagged as invalid for reporting across all tools (0 errors). - currency: All tools specified USD, EUR, and INR with exact FX multipliers. GBP appeared 0 times (0 errors). - cancel_reason & status: Accurately documented across all layers.

5. Methodological Limitations & Integrity Caveats

  1. Reviewer Blindness Status: NOT VERIFIED - The six review sessions were run sequentially by an automated agent process in a single execution pipeline rather than separate human reviewers in isolated chats. Cognitive isolation from prior harness context is not verified.
  2. First Attempt Non-Blind & Quarantined: - The initial attempt (archived as attempt1) was executed in the main workspace with access to test files and review logs, and contained factual errors (e.g., plan tiers as 'pro'/'enterprise' and 'GBP' currency). These layers were quarantined, and attempt 2 was re-run from clean starting layers.
  3. Post-Hoc Rules Revision (Rules v2): - The initial baseline benchmark was run with business_rules.md v1. Rules v2 clarified date windows (half-open, no BETWEEN), cash-basis refund netting, and plan_tier distinction. Baseline and control numbers were re-benchmarked against rules v2 for consistency.
  4. Excluded Olist Questions: - Three questions (olist-012, olist-016, olist-017) were excluded from the scored suite due to schema/semantic ambiguities in the raw Brazilian e-commerce dataset, leaving 18 scored questions (plus 1 ambiguous question olist-013).
  5. Connector & Tool Versions: - Datus was evaluated using datus-agent 0.4.3 with datus-postgresql 0.1.9. - Wren Engine was evaluated using wren-engine 0.6.0. - ktx was evaluated using @kaelio/ktx 0.16.0.
  6. Agent Execution Time vs. Human Effort: - Review sessions took between 1 and 13 minutes of automated agent execution. This measures script execution time, not human engineering effort, and cannot be used to assess the labor cost of semantic layer authoring.
  7. The Shared Document Upper Bound: - The answer-key gold SQL queries and the reviewed semantic layers were both authored from the identical requirements document (docs/business_rules.md). Therefore, this study measures how well tools carry known rules, not whether tools can discover unwritten business logic.
  8. Sample Size Constraints: - With 32 appdb questions and 18 olist questions, the minimum detectable effect size is approximately 3 questions on appdb and 2 questions on olist. Differences smaller than this are indistinguishable from noise.
  9. Commit Provenance of Benchmark Numbers: - Baseline, out-of-the-box context layers, and control benchmarks were executed at commit 124585c (tagged study-v1). - Initial reviewed layers audit and drop-in split were recorded at commit ea085f2 (tagged study-v1.1). - Patched Wren runner (with sqlglot dialect transpilation), 3-run Wren re-evaluation, regenerated paired statistics, and final scoreboard numbers were produced at commit study-v1.2.

6. Next Steps: Proposal for Rule Induction & Verification

Because the rules are the primary lever, the highest-leverage unsolved problem in data agent reliability is extracting and verifying implicit business rules from production environments:

flowchart TD
    A[Raw Schema & DDL] --> D[Rule Induction Engine]
    B[Query History / BI Logs] --> D
    C[Database Profiling & Constraints] --> D
    D --> E[Candidate Rules Generation]
    E --> F[Automated Data Verification]
    F -->|Verify against DB| G[Verified Business Rules]
    G --> H[Harness Evaluation: dbeval]

Proposed Next Experiment:

  1. Target: Attempt to recover the 14 known appdb business rules (test flags, soft deletes, plan tiers, cents conversion, churn definitions, refund netting) without access to docs/business_rules.md.
  2. Inputs: Database contents, information schema, and a synthetic query log of 100 historical queries.
  3. Mechanism: An induction pipeline that generates candidate rules (e.g. "Should is_test = true be excluded from reporting?"), verifies candidate filters against table distributions, and compiles an automated rules.md.
  4. Evaluation: Score the induced rules through the existing dbeval benchmark harness to measure rule recovery precision, recall, and end-to-end downstream SQL accuracy.

7. Upstream Issues Filed & Proposed Fixes

In addition to benchmark scoring, dbeval functioned as an active testing harness for the evaluated open-source tools. Rigorous evaluation against real-world schemas uncovered two failure modes in upstream repositories. Issues were filed and fixes were proposed in upstream pull requests (both open, not merged):

1. @kaelio/ktx — Silent Enrichment Failure & Cache Poisoning

  • Issue Filed: kaelio/ktx#377
  • Proposed Fix in PR: Kaelio/ktx#378 (open, not merged)
  • Failure Mode: When external LLM provider calls fail completely during local schema enrichment (e.g. gateway 404 from /language-model, rate limits, or bad credentials), local-enrichment.ts reported completed with exit code 0, cached empty/null results in descriptions.json and SQLite scan:descriptions, and bypassed per-table resume on subsequent runs in ktx 0.16.0.
  • Proposed Fix: Adds total failure detection, truthful non-zero exit status reporting, Windows SQLite handle cleanup, and prevents incomplete cache short-circuiting so subsequent runs resume incomplete tables.

2. Datus (datus-postgresql) — Foreign Key Omission in Reconstructed Table DDL

  • Issue Filed: Datus-ai/Datus-agent#1542
  • Proposed Fix in PR: Datus-ai/datus-db-adapters#177 (open, not merged)
  • Failure Mode: In PostgreSQLConnector._get_ddl(), constraint extraction was restricted to c.contype IN ('p', 'u'), completely omitting 'f' (foreign keys). Reconstructed table DDL stored in schema_metadata.json and indexed in LanceDB contained zero foreign key relationships, forcing downstream models to guess join keys from column names alone.
  • Proposed Fix: Expands constraint extraction to contype IN ('p', 'u', 'f'), orders constraints deterministically (PRIMARY KEY $\rightarrow$ UNIQUE $\rightarrow$ FOREIGN KEY), and cleanly separates unvalidated (NOT VALID) foreign keys into standalone ALTER TABLE statements to maintain valid PostgreSQL execution grammar.
